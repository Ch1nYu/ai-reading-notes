## 完整摘要

### 長上下文為何會降低 Coding Agent 的推理品質
程式碼助理（Coding Agent）每讀取一個檔案、執行一次搜尋或修改一段程式碼，都會將過程與結果追加至對話歷史，之後每次請求都完整攜帶這些內容，導致歷史只增不減、成本與延遲越來越高。各家模型在大海撈針（NIAH）等測試中能拿接近滿分，但這類測試只考字面檢索，不代表語義理解與推理在長上下文中依然可靠。Chroma 的上下文腐化（context rot）研究讓 18 個模型在固定任務難度下只增加輸入長度，結果全部模型效能隨輸入變長而下降，且下降幅度不均。研究特別指出兩點對 Coding Agent 致命：一是主題相關但無法回答問題的干擾項（distractor），即使只有一條也會明顯拉低效能，輸入越長下滑越明顯，而長會話歷史充滿此類半相關片段；二是 LongMemEval 對比顯示，僅給相關片段時模型表現良好，但換成完整 11 萬 token 的歷史後效能大幅下滑，因為模型必須在同一輪同時完成從長歷史中檢索相關內容、再基於找到內容推理這兩件事，檢索與推理互相擠佔資源。這些發現的限制在於，研究主要以合成或固定難度任務呈現，未必完全對應真實開發場景中的所有編程工作。

### Pi 上下文膨脹與視窗滿時的兩種動作
Pi 發給模型的每次請求，都會攜帶系統提示詞（system prompt）、AGENTS.md、工具定義以及完整的對話歷史。舉例來說，使用者要求模型修改一個 bug，模型先調用 read 工具查看檔案，Agent 結束後將檔案內容拼回請求再發送一次，模型看完可能又調用 grep，來回數輪才給出答案。一個 turn（對話輪次）內每次請求都帶著之前的一切，包括檔案內容、搜尋結果、模型自身的中間想法等等。歷史只增不減，越往後越貴也越慢，總有一天下一次請求會超出視窗上限，回報類似「Request exceeds the maximum size」的錯誤，會話因此無法繼續。此時 Pi 提供兩種動作：一種是直接開新會話，歷史清零，之前的決策與未完成任務全部丟掉；但結合上下文腐化的觀點，爛掉的上下文有時比沒有上下文更傷模型狀態，丟掉歷史反而是正確選擇。另一種則是上下文壓縮（compaction），把舊歷史交給一次 LLM 請求壓縮成摘要，用摘要取代原內容，給新消息騰出空間，讓會話得以繼續。這兩種動作的限制在於，開新會話會喪失先前決策脈絡，而壓縮則無法保留所有細節。

### Pi 的壓縮流程與摘要內容
Pi 在每個 turn 結束後檢查上下文佔用，接近視窗上限就會自動觸發壓縮，使用者也能手動輸入 /compact 隨時觸發。此外還有一種兜底機制：當 turn 跑到一半撞上溢出錯誤時，Pi 會當場壓縮再繼續，避免任務直接報廢。壓縮時機選在 turn 結束有其考量，因為 turn 還在跑時每次請求都在前一次基礎上追加，LLM 的提示詞快取（prompt caching）前綴能一直複用，此時壓縮對快取損失最小。壓縮並非全部刪除，Pi 會保留最近一段消息原樣不動，保留量由可配置的 token 預算控制，預設 2 萬，約等於 5 到 20 個 turn；在此之前的內容全部序列化，交給一個獨立的 LLM 請求去總結。這個摘要請求與平常對話有三處不同：系統提示詞變更，告訴模型它是一個上下文總結助手；使用者訊息變更，要求輸出涵蓋目標、進展與關鍵決策的結構化摘要；請求本身獨立於會話歷史，因此可以換一個較便宜的模型來跑，不佔用主對話的成本。摘要以純文字存回會話，因此可移植，Pi 內換模型時新模型可直接沿用同一份摘要，無需重新壓縮。Pi 也可擴充，作者預留實驗入口讓 Pi 自行撰寫擴充功能來替換預設壓縮提示詞，以測試不同摘要策略；作者認為 compaction 沒有標準答案，目前實作只是其認為的最佳做法。這段流程的限制在於，摘要品質依賴總結模型與提示詞設計，且預設 token 預算對應的實際摘要長度與後續推理品質，原文未有定量說明。

### 壓縮的隱藏代價與作者取捨
提示詞快取（prompt caching）仰賴前綴精確比對來節省成本，LLM 供應商會對命中快取的部分給予極低折扣，例如 DeepSeek V4 Flash 在命中快取時幾乎不要錢。但在壓縮之後，雖然保留的那段 turn 內容沒有變，但它前面的前綴已變成系統提示詞直接接上摘要，前綴改變後此前累積的快取全部作廢，壓縮後的第一個請求需要重新計算，之後的新請求才能重新累積快取。因此壓縮是有隱性成本的，壓縮做得越頻繁，快取重建的成本就越多。上下文壓縮中有三個變數互相牴觸：信息保真度、上下文長度、快取命中率。壓縮頻率高時，上下文確實變短，但快取反復作廢，摘要過程也必然丟掉一部分細節；壓縮頻率低時，快取命中率較高，但模型會長時間處於超長上下文中，降智與幻覺問題會更明顯。作者 LanLance 的做法是查看前後內容的相關性：如果前面聊過的內容後面仍會用到，compaction 才值得做；如果前後話題已經不相關，作者會直接清除並開啟新會話，完全不需要摘要。作者強調，摘要丟掉的細節在壓縮時無人知道哪條以後會用上，本質是一次有損壓縮，細節消失不可逆。這套取捨的限制在於，它依賴使用者自行判斷前後相關性，且原文未給出壓縮頻率與快取命中率的定量關係，讀者難以量化壓縮對成本的具體影響。

## 重點知識與概念拆解

| 概念 | 白話解釋 | 來源證據 |
|------|----------|----------|
| 上下文腐化（context rot） | 長上下文會讓模型在語義理解與推理任務上的表現下降，即使基測顯示檢索能力良好；輸入越長，模型越容易被無關或半相關內容干擾，推理品質因此受損。 | Chroma 的研究測試 18 個模型，在任務難度固定、僅增加輸入長度的條件下，全部模型效能皆隨輸入變長而下降，且下降幅度不均；大海撈針（NIAH）只考字面檢索，無法反映真實推理場景。 |
| 干擾項（distractor） | 與問題主題相關但無法直接回答問題的內容，即使只有一條，也會明顯降低模型效能，輸入越長下滑越明顯；長會話歷史中充滿此類半相關片段，容易稀釋模型注意力。 | 原文將此列為對 Coding Agent 場景尤其致命的兩個研究結論之一，說明長對話歷史會讓模型在雜訊中難以聚焦。 |
| LongMemEval | 僅提供相關片段時模型表現良好，但改用完整 11 萬 token 的歷史時效能大幅下滑，原因是模型必須在同一輪同時進行檢索與推理，兩項任務互相擠佔資源。 | 原文引用 LongMemEval 對比，指出只有相關片段時模型表現很好，完整歷史則導致明顯效能下降。 |
| 上下文壓縮（compaction） | 將舊對話歷史交給單獨的 LLM 請求壓縮成摘要，用摘要取代原始內容，為新消息騰出視窗空間，讓會話得以繼續而不立即中斷；壓縮不會刪除所有舊內容，會依 token 預算保留最近一段訊息。 | Pi 在每個 turn 結束檢查佔用，接近上限自動觸發；也可手動輸入 /compact；mid-turn 撞上溢出錯誤時會當場壓縮再繼續。保留量預設為 2 萬，折合 5 到 20 個 turn。 |
| 提示詞快取失效（prompt caching invalidation） | 壓縮後保留的 turn 內容未變，但前綴從系統提示詞接上摘要，導致之前累積的快取全部失效，壓縮後第一個請求需重新計算，之後的請求才能重新累積快取，因此頻繁壓縮會增加隱性成本。 | 原文以 DeepSeek V4 Flash 為例說明命中快取時幾乎不要錢，並指出壓縮後前綴改變使之前的快取全部作廢。 |
| 有損壓縮（lossy compression） | 摘要過程會丟掉細節，壓縮時無法預知哪條細節以後會用上，被遺失的細節無法復原，本質上是不可逆的有損壓縮。 | 作者表示「摘要丟掉的細節，壓縮的時候誰也不知道哪條以後會用得上，本質是一次有損壓縮，細節消失不可逆」。 |
